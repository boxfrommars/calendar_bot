# Deployment requirements: calendar-bot

Контракт описывает требования приложения и проверяемый результат. Конкретное
размещение, запуск процесса, хранение секретов и реализацию backup определяет
окружение размещения. Все пути ниже относительны корню приложения либо заданы
через переменную окружения.

## Приложение

| Параметр | Значение |
| --- | --- |
| Название | `calendar-bot` |
| Репозиторий | `git@github.com:boxfrommars/calendar_bot.git` |
| Production-ветка | `master` |
| Канонический URL | Не применимо: собственного HTTP-интерфейса нет |
| Тип процесса | Один длительно работающий процесс: polling и планировщик |
| Runtime | Python 3.14+; целевая версия 3.14 |
| База данных | SQLite, версия схемы 2 |

## Runtime-интерфейс

- Package manager: pip. Команды ниже выполняются Python из окружения приложения
  и из корня checkout.
- Установка production-зависимостей:

  ```sh
  python -m pip install --require-hashes -r requirements.txt
  ```

- Команда запуска: `python -m calendar_bot run`.
- Локальная проверка работающего polling: `python -m calendar_bot health`.
- Относительный публичный каталог: не применимо. Frontend-сборка и её выходные
  артефакты отсутствуют; входящие HTTP-порты не нужны.
- Нужны стандартный модуль SQLite, TLS CA certificates, исходящий HTTPS к
  Telegram Bot API и OpenAI API, файловая система с поддержкой SQLite WAL и
  блокировок файлов. На Linux приложение использует `fcntl.flock`. IANA timezone
  data предоставляются пакетом `tzdata`, если отсутствуют в ОС.
- Один процесс на Telegram-токен; один процесс записи на `DATABASE_PATH`.
  `run` и `migrate` используют OS-lock рядом с БД. Настроенный на токене webhook
  блокирует запуск; приложение не удаляет его автоматически.
- SIGTERM/SIGINT завершают polling и планировщик. Обработчики завершаются в
  пределах 45 секунд, отправка — до 15 секунд. Окружение должно давать не менее
  70 секунд на штатную остановку и перезапускать процесс при ненулевом exit code.
  Polling останавливается явно до закрытия SDK и БД; неожиданное завершение
  polling или работника также считается ошибкой.
- Версия Python 3.14 является основной целевой; автономный набор тестов должен
  пройти на целевой платформе до активации.

## Конфигурация

Переменные окружения имеют приоритет над локальным `.env`. Параметр
`--env-file` выбирает другой локальный файл; приложение никогда не перезаписывает
конфигурацию и не выводит секреты.

| Переменная | Обязательна | Секрет | Назначение и инвариант |
| --- | --- | --- | --- |
| `BOT_TOKEN` | Для `run` и `check`, включая `--offline` | Да | Токен отдельного Telegram-бота; отсутствие webhook обязательно для `run` |
| `OPENAI_API_KEY` | Для `run` и `check`, включая `--offline` | Да | OpenAI API-ключ; `check` проверяет только его наличие |
| `OPENAI_MODEL` | Нет | Нет | Непустое имя; default кода — `gpt-5.4-mini-2026-03-17`. Нужны Responses API, Structured Outputs и `reasoning.effort=low` |
| `ALLOWED_USER_IDS` | Нет | Нет | Положительные числовые ID через запятую; пустой список не даёт никому доступ к календарю |
| `DATABASE_PATH` | Нет | Нет | Постоянный файл SQLite; default `data/calendar.sqlite3`; относительный путь разрешается от рабочего каталога; пустое значение и `:memory:` запрещены |
| `PYTHONDONTWRITEBYTECODE` | Рекомендуется для read-only кода | Нет | Значение `1` исключает запись Python bytecode в checkout |
| `NOTIFY_SOCKET` | При включённом watchdog systemd | Нет | Передаётся менеджером службы; Unix datagram socket с файловым или абстрактным адресом |
| `WATCHDOG_USEC` | При включённом watchdog systemd | Нет | Передаётся менеджером службы; положительный интервал в микросекундах; отсутствие или `0` отключает watchdog |
| `WATCHDOG_PID` | Нет | Нет | Если задан, уведомления отправляет только процесс с этим PID; значение передаётся менеджером службы |

Для `migrate` ключи API не нужны; остальные параметры конфигурации должны быть
корректны. В [.env.example](.env.example) явно выбрана модель `gpt-6-luna`;
копирование примера задаёт её вместо default кода.
`health` использует только `DATABASE_PATH`; остальные application-параметры и
ключи API ей не нужны. Watchdog-переменные не требуется добавлять в локальный `.env`.

Изменения переменных применяются после перезапуска. Личные часовые пояса,
интервалы и настройки сводки хранятся в SQLite. При первом заполнении списка
разрешений бот с пустым списком может показать пользователю его собственный ID;
AI и календарные данные при этом недоступны.

## Состояние и запись

- Единственное постоянное хранилище — `DATABASE_PATH`: пользователи, диалоги,
  черновики, события, дела с датами и отметками выполнения, исключения, вхождения,
  очередь и результаты отправок. Удалённые дела сохраняются с признаком удаления.
- Просмотр будущих недель вычисляет вхождения из серии и исключений без добавления
  записей в БД или очередь, в том числе за 30-дневным горизонтом подготовки.
  История встреч использует сохранённые вхождения, история дел — их исходные даты
  и текущие отметки выполнения. Контекст правок сохраняет выбранный период и страницу.
- Runtime нужна запись в `DATABASE_PATH` и содержащий его каталог для файлов
  `DATABASE_PATH-wal`, `DATABASE_PATH-shm`, `DATABASE_PATH.lock`,
  `DATABASE_PATH.health.json` и временного `DATABASE_PATH.health.json.tmp`. Файл lock может
  оставаться после остановки; занятость определяется OS-lock, а не его наличием.
- Health-снимок атомарно заменяется каждые 5 секунд и при смене фазы процесса.
  Он содержит только технические времена, тип ошибки и идентификатор запуска,
  связанный с OS-lock. Health-файлы и содержимое lock воспроизводимы; не включать
  их в backup и не восстанавливать как свидетельство работающего процесса.
- Генерируемые артефакты runtime — вспомогательные файлы SQLite, lock и health. WAL может
  содержать ещё не перенесённые в основной файл данные и не является обычным
  воспроизводимым кешем.
- При `PYTHONDONTWRITEBYTECODE=1` код и установленные зависимости могут быть
  read-only. Иначе Python может создавать `__pycache__/` при импорте. Установка
  зависимостей пишет в выбранное виртуальное окружение, локально — `.venv/`.
- Пользовательских загрузок, публичных артефактов, отдельной сборки и обязательного
  дискового кеша приложения нет. Виртуальное окружение воспроизводится из lock
  и не заменяет backup постоянных данных.
- Логи идут в stdout/stderr и содержат технические ID, результаты доставки и
  безопасные типы ошибок. Нужны хранение и ротация логов средствами окружения.
- Backup должен быть согласованным: SQLite backup API или команда `.backup`.
  Обычная копия работающего файла не гарантирует включение WAL.
- Проверка копии: `PRAGMA integrity_check` возвращает `ok`,
  `PRAGMA foreign_key_check` — пустой результат. Пробное восстановление выполняется
  в отдельный файл с проверкой схемы и сохранённого расписания, без запуска второго
  polling-процесса. Нельзя смешивать восстановленную БД с WAL/SHM от другой копии.
- Восстановление старой БД возвращает также старый журнал доставок; для ещё
  актуальных событий после восстановления возможны повторные уведомления.

## Lifecycle hooks

### Автономные тесты

- Момент выполнения: после установки зависимостей, до активации.
- Команда:

  ```sh
  python -m unittest discover -s tests -q
  ```

- Эффект: проверено поведение приложения с временными БД и подставными API.
- Изменяемые пути: временные каталоги тестов, Python bytecode при его разрешении.
- Изменение постоянных данных: отсутствует; тесты используют временные БД.
- Повторный запуск безопасен: да.
- Ошибка блокирует релиз: да, ненулевой exit code. Сеть и секреты не требуются.

### Preflight

- Момент выполнения: после явной инициализации или необходимой миграции БД,
  до активации процесса.
- Команда:

  ```sh
  python -m calendar_bot check
  ```

- Эффект: проверены наличие конфигурации, версия схемы, целостность и foreign keys
  SQLite, Telegram `getMe`. Проверка не запускает polling и не отправляет сообщения.
- Изменяемые пути: БД открывается в режиме `mode=ro`; SQLite может обслуживать
  вспомогательные WAL/SHM-файлы согласно своему режиму работы.
- Изменение постоянных данных: отсутствует; нет записи событий и результатов
  доставки.
- Повторный запуск безопасен: да.
- Ошибка блокирует релиз: да, ненулевой exit code.
- `--offline` пропускает Telegram и пригоден для локальной диагностики, но не
  заменяет сетевой preflight. Доступность модели OpenAI и отсутствие webhook
  эта команда не проверяет; webhook проверяется при `run`.

### Проверка после запуска

- Момент выполнения: после запуска процесса и первого успешного `getUpdates`,
  до признания релиза работоспособным.
- Команда: `python -m calendar_bot health` с тем же `DATABASE_PATH`, что у процесса.
- Эффект: подтверждены текущий владелец OS-lock и свежий успешный ответ polling.
- Команда загружает только код чтения состояния и лёгкие зависимости CLI;
  aiogram, OpenAI SDK, Pydantic, HTTP-клиенты и runtime бота не импортируются.
- Изменяемые пути: отсутствуют; при запрете bytecode команда не записывает файлы.
- Изменение постоянных данных: отсутствует; SQLite и внешние API не открываются.
- Повторный запуск безопасен: да; до первого успеха результат неуспешный.
- Ошибка блокирует признание релиза работоспособным: да, код `1`. Повторные
  проверки и оповещение организует окружение; не использовать их как основание
  для автоматического рестарта при недоступности Telegram.

## Изменения данных

Миграции отделены от обычного запуска и воспроизводимых hooks:

```sh
python -m calendar_bot migrate
```

### Первичная инициализация

- Команда создаёт схему 2 в отсутствующей БД либо в пустой БД без таблиц.
  Заполненная БД без версии схемы не принимается.
- Каталог `DATABASE_PATH` должен допускать создание БД и файла lock. Другой
  процесс бота или миграции не должен удерживать тот же lock.
- Повтор команды на схеме 2 безопасен и не меняет данные. `run` и `check`
  отсутствующую БД не создают. Инициализация нужна до первого запуска;
  пользовательских данных для backup на этом этапе ещё нет.

### Изменение существующих данных

- Объединение списков в «Сегодня» и «7 дней» сохраняет схему **2**, зависимости
  и runtime-интерфейс. Для БД версии 2 дополнительных миграций не требуется.
- Текущий код явно мигрирует схему **1 → 2**: добавляет таблицу дел, индекс и
  тип записи/ссылку на дело в черновиках. События, исключения, запросы и очередь
  сохраняются; старые черновики остаются событиями и требуют подтверждения.
  Миграция выполняется одной транзакцией. Рабочая БД должна иметь версию 2;
  неизвестные версии и заполненная БД без версии блокируют `migrate`.
- Новые миграции добавляются явно. Предусловия — согласованная проверенная
  backup-копия и остановленный процесс записи. `migrate` использует тот же
  exclusive OS-lock, что и runtime; оно не является обычным hook каждого релиза.
- Обратные миграции и автоматическое восстановление отсутствуют. Совместимость
  старого и нового кода с данными описывается при каждом изменении схемы или
  сериализованного состояния.
- Ожидаемая недоступность включает остановку процесса, миграцию и запуск. Переход
  1 → 2 не пересоздаёт события и очередь; длительность зависит от числа черновиков
  и скорости SQLite-хранилища. Перед применением измерить её на согласованной
  копии в отдельной среде и учесть результат в окне обновления.

## Внешнее поведение

HTTP-интерфейс, canonical URL, дополнительные HTTP-имена, redirects, health
endpoint и обработка неизвестного URL не применяются; правил сохранения HTTP
path/query нет. Бот отвечает только в личных Telegram-чатах. Неизвестная команда
получает подсказку `/help`; расписание пользователя недоступно другим пользователям.

Основное меню содержит «Сегодня», «7 дней», «События» и «Настройки».
«7 дней» открывает сегодня и шесть следующих дней; прошлые и будущие периоды,
включая пустые, доступны шагом в семь дней. Страницы по восемь записей отделены
от выбора периода. Просрочка показана отдельным блоком только в периоде,
содержащем сегодняшний день. Старые `/tasks`, «Дела» и переходы к прежним спискам
направляют в «7 дней» без AI; старые кнопки действий сохраняют проверки доступа
и версии. Новые и старые кнопки сводки отправляют «Сегодня» отдельным сообщением.

Наблюдаемые признаки работы — длительно работающий процесс, сообщения
`bot_started`/`bot_stopped`, безопасные ошибки polling, результат `health` и ответы
на тестовые Telegram-события. Живой процесс и успешный `check` не подтверждают
работоспособность polling. Успешный `health` подтверждает получение обновлений,
но не разбор OpenAI или доставку напоминаний: их проверяет smoke-сценарий.

### Контроль polling

`health` возвращает код `0`, только когда OS-lock принадлежит запуску из снимка,
фаза — polling, возраст снимка не превышает 15 секунд, а последний успешный
`getUpdates` был не более 120 секунд назад. Пустой ответ считается успехом.
До первого успеха, после остановки, при старом, повреждённом или чужом снимке
возвращается код `1`. Вывод содержит безопасную причину, возраст последнего
успеха в секундах и тип последней ошибки. Для интервалов используются монотонные
часы; изменение календарного времени их не сбрасывает.
Проверка выполняется модулем `health.py`, отделённым от middleware в `polling.py`.
Оптимизация импортов не меняет формат снимка и результата, проверку владельца
lock, пороги или протокол watchdog; дополнительная миграция данных не требуется.

Логи `polling_request_failed` содержат тип исключения, число последовательных
ошибок и длительность запроса, без исходного текста исключения и traceback.
Первая ошибка и смена типа видны сразу, повтор одного типа — не чаще раза в
60 секунд. `polling_recovered` фиксирует восстановление. `TelegramConflictError`
попадает в эти логи; aiogram сохраняет свой механизм повторов с backoff.

Watchdog проверяет прогресс попыток, включая завершения с ошибкой. Он не зависит
от свежести успешного ответа и не вызывает циклические рестарты при сетевой
аварии. Для окружения требуется внешний watchdog с интервалом 30 секунд и
перезапуск при отказе; для systemd этому соответствуют `WatchdogSec=30s`,
`NotifyAccess=main`, `Restart=on-failure`. Поддерживается существующий тип запуска
`exec`; приложение не требует протокола `READY=1`. Менеджер службы передаёт
watchdog-переменные окружения и обеспечивает доступ к notify-сокету.

Уведомления `WATCHDOG=1` отправляются из основного event loop с периодом
`min(5 секунд, WatchdogSec / 2)`. Через 90 секунд без начала или завершения
`getUpdates` приложение пишет `polling_stalled` и прекращает уведомления.
Длительность запроса ограничена 70 секундами: 60 секунд сетевого таймаута плюс
10 секунд long polling. На начальную загрузку выделены отдельные 90 секунд.
При полном зависании event loop уведомления прекращаются сразу; при зависании
только polling внешний watchdog срабатывает после прекращения уведомлений.
При остановке приложение отправляет `STOPPING=1` и завершает задачи перед
закрытием соединений. Без systemd `health` и логи доступны, внешний рестарт
нужно обеспечивать отдельно.

Применение настроек службы и мониторинга принадлежит окружению размещения;
данный контракт не изменяет инфраструктуру сам по себе.

| Smoke-сценарий | Ожидаемый результат |
| --- | --- |
| `/start` разрешённого пользователя | Выбор пояса либо готовность к добавлению, меню «Сегодня», «7 дней», «События», «Настройки» |
| `/start` постороннего | Отказ и собственный Telegram ID, без доступа к данным |
| Событие через несколько минут | Автосохранение, карточка с изменением/удалением и запланированные напоминания |
| Повторная обработка сообщения | Событие не дублируется; напоминание приходит в выбранное время |
| Изменение и удаление из карточки | Правки требуют подтверждения; удаление отменяет будущие напоминания |
| `/today`, `/week`, `/events` | Личное расписание и рабочие кнопки управления |
| Дело без времени / без даты | Автосохранение на указанную дату / местное сегодня; отдельных напоминаний нет |
| «Сегодня», «7 дней» | Внутри дня встречи по времени, невыполненные дела, выполненные; просрочка отдельным блоком без дублей |
| Листание недель и страниц, включая пустой период | Заголовок с выбранными датами, шаг в семь дней, возврат к ближайшим дням; новый период открывается с первой страницы |
| Листание назад | Сохранённые встречи и выполненные дела на своих датах, без повторного создания истории по текущей серии |
| Просмотр повтора дальше 30 дней | Карточка учитывает переносы и отмены; просмотр не меняет вхождения и очередь |
| Изменение или удаление дальней встречи/дела | Подтверждение и проверки владельца/версии; выбранный период сохраняется, страница корректируется |
| Полночь или смена пояса при открытом расписании | Кнопки сохраняют даты периода; часовой пояс определяет границы дней и текущую просрочку |
| Старые `/tasks`, «Дела» и списки дел | Открывается «7 дней» без AI; старая кнопка «Дела» обновляет основное меню |
| Выполнение, возврат, изменение и удаление дела | Выполнение и возврат одним нажатием; правки и удаление после подтверждения; устаревшая кнопка не меняет данные |
| Напоминание о событии | Внизу актуальные раздельные счётчики сегодняшних и просроченных дел; повтор после ошибки пересчитывает их |
| Перенос/отмена одной встречи | Остальные повторы сохранены; старое уведомление не отправляется |
| Настроенная сводка | События местного дня, невыполненные дела на сегодня и просрочка; «Открыть сегодня» присылает актуальное расписание отдельно, не редактируя сводку; выполненные исключены |
| Штатный перезапуск | Сохранённые события продолжают работать; записанные в БД отправки не повторяются, длинная сводка продолжается с сохранённой части |
| Пустой успешный `getUpdates` | `health` успешен; пользовательских сообщений для проверки не требуется |
| Длительная сетевая авария / конфликт токена | Безопасные ошибки в журнале, `health` неуспешен после устаревания успеха; повторы и watchdog-уведомления продолжаются |
| Зависание polling или event loop | Watchdog-уведомления прекращаются, внешний supervisor завершает и перезапускает процесс |

Интервал проверки очереди — 5 секунд; фактическая задержка зависит от доступности
Telegram и ограничений API. Недоступность OpenAI влияет на ввод, но не на уже
сохранённые напоминания. Ошибка фонового работника завершает весь процесс с
ошибкой. Контроль состояния процесса, перезапусков и свежести backup обеспечивает
окружение; код не создаёт сторонних каналов оповещения администратора. Если
Telegram принял сообщение, а подтверждение не попало в БД, при повторе возможен
дубль: строгая однократная доставка на этой границе не гарантируется.

## Проверка релиза

Обязательны [автономные тесты](#автономные-тесты) на целевой платформе Python 3.14,
[preflight](#preflight) и [проверка после запуска](#проверка-после-запуска);
их команды и условия приведены выше. Проверки стиля
для разработки описаны в [README.md](README.md#проверки).

Перед первой эксплуатацией нужны smoke в отдельном тестовом боте и пробное
восстановление согласованной SQLite-копии. При смене модели также проверяется
разбор реальных примеров; `python -m calendar_bot.evaluation` — отдельная платная
проверка OpenAI, описанная в README. Эти действия не выполняются автоматически
при запуске приложения. Автономные проверки Windows не заменяют проверку
на целевой Linux-платформе.
Перед активацией watchdog проверить его фактическое срабатывание в отдельной
Linux-среде: зависание запроса и блокировка event loop должны приводить к рестарту,
а продолжающиеся неуспешные попытки Telegram — сохранять работающий процесс.
Протокольный тест настоящего Unix datagram socket выполняется только на Linux.

## Совместимость rollback

- Возврат кода без возврата данных допустим, если выбранная версия понимает
  схему 2 и текущие форматы событий, дел, черновиков и очереди. Совпадение номера схемы
  само по себе не доказывает совместимость сериализованных данных.
- Навигация по периодам не меняет схему 2 или формат очереди. После возврата к
  коду без такой навигации новые кнопки с датами могут перестать работать;
  `/start` и команды открывают интерфейс возвращённой версии.
- Требования к Python и зависимостям должны соответствовать возвращаемому коду.
  Текущий контракт рассчитан на Python 3.14; downgrade БД приложение не выполняет.
- Поддержка дел добавлена миграцией 1 → 2. Старый код со схемой 1 не запустится с новой БД:
  для такого rollback нужна согласованная копия до миграции. Более поздние изменения,
  включая новые дела и результаты отправок, при восстановлении этой копии теряются.
  Обратной миграции нет. Формат `notifications.parts` остаётся массивом строк;
  начатые сводки и их `part_index` сохраняются, старое оформление поддерживается.
- При возврате к коду без watchdog/health окружение должно отключить соответствующий
  watchdog и проверки до запуска старой версии.
- Application-команды после возврата совместимого кода: preflight
  `python -m calendar_bot check`, затем запуск обычной командой `run`.
  Миграция для совместимой схемы 2 не требуется.
- Восстановление данных требуется при несовместимости кода или повреждении БД;
  оно допускается только при остановленном процессе записи из согласованной
  проверенной копии. При этом откатывается и журнал доставок, что может привести
  к повторным уведомлениям.
- Несовместимость новых миграций и форматов описывается в изменении, которое их
  вводит. Проверки после возврата — preflight, существующее расписание, тестовое
  напоминание и продолжение сохранённой очереди. Автоматического rollback нет.

Выбор версии и действия окружения по переключению релиза в этот контракт
не входят.

## Когда обновлять этот документ

При изменениях runtime, production-зависимостей, конфигурации, команд запуска,
записываемых данных, lifecycle hooks, миграций, внешнего поведения или совместимости
rollback. Конкретное размещение и серверные действия в контракт не включаются.

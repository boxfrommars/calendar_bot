# Разработка и диагностика

[Обзор и локальный запуск](../README.md) · [Руководство пользователя](usage.md) ·
[Контракт размещения](../DEPLOYMENT.md) · [Журнал работ](journal/README.md)

Команды ниже выполняются на Linux из корня репозитория в виртуальном окружении
Python 3.14 с установленными зависимостями проекта. Первичная настройка описана
в [README](../README.md#быстрый-локальный-запуск). В каждой новой оболочке активируйте
подготовленное окружение:

```sh
. .venv/bin/activate
```

Правила внесения изменений находятся в [AGENTS.md](../AGENTS.md).

## Устройство кода

| Часть | Ответственность |
| --- | --- |
| [domain.py](../calendar_bot/domain.py) | События, дела, источники времени, календарная арифметика, повторы и DST |
| [parser.py](../calendar_bot/parser.py) | Структурированный разбор OpenAI и проверка происхождения поисковых ссылок |
| [storage.py](../calendar_bot/storage.py), [service.py](../calendar_bot/service.py) | Схема SQLite, транзакции, права владельца, черновики, события, дела и постоянная очередь |
| [telegram.py](../calendar_bot/telegram.py), [presentation.py](../calendar_bot/presentation.py) | Команды и кнопки, диалоги, шаблоны сообщений и Telegram entities |
| [worker.py](../calendar_bot/worker.py) | Доставка уведомлений и сводок, повторы после ошибок |
| [polling.py](../calendar_bot/polling.py), [health.py](../calendar_bot/health.py), [systemd.py](../calendar_bot/systemd.py) | Наблюдение за polling, чтение технического состояния, watchdog-протокол |
| [runtime.py](../calendar_bot/runtime.py), [__main__.py](../calendar_bot/__main__.py) | Запуск и остановка задач, CLI с отложенными импортами |
| [model_trace.py](../calendar_bot/model_trace.py) | Опциональная запись запросов и ответов модели в отдельные диагностические файлы |

После проверки доступа текст поступает в parser. Модель возвращает типизированный
список, domain проверяет календарные поля, а service сохраняет весь список и
напоминания одной транзакцией. Повторная обработка исходного сообщения не создаёт
новые записи. У модели нет прямого доступа к БД или инструментам изменения календаря.
При редактировании ей передаётся только выбранная запись вместе с диалогом.
Разбор использует [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
и `store=False`; это не обещание нулевого хранения данных провайдером.

Общий блок промпта содержит правила полей, дат, ограничений и уточнений. При
добавлении используется блок с правилами веб-поиска. Для редактирования
поисковый блок заменён явным порядком изменения выбранной записи: сохранить
остальные поля и вернуть одну запись либо уточнение. Режим определяется наличием
`selected_item`; отдельного модельного классификатора нет.
Рабочая модель и общий default приложения и evaluation —
`gpt-6-luna`; `OPENAI_MODEL` может явно переопределить его.

При внутренней перепроверке прошедшего веб-результата parser держит проверенный
снимок первой попытки и индексы перепроверяемых событий только в текущем вызове
`parse`. У этих событий разрешено исправлять дату, время, пояс и источник;
`time_source=web` и ссылка из текущей попытки обязательны даже при подтверждении
прежнего времени. Остальные поля, состав и порядок списка должны сохраниться.
Источник из первой попытки разрешён только для полностью неизменённой записи
на той же позиции, не требующей перепроверки. Старые URL не образуют общий список
разрешённых ссылок; `question_sources` всегда проверяются по текущей попытке.
История диалога и предыдущие вызовы `parse` не подтверждают источник. Нарушение
этих условий приводит к уточнению без частичного сохранения. Бюджет перепроверки
остаётся общим с первой попыткой, см. [конфигурацию и лимиты](../DEPLOYMENT.md#конфигурация).

Относительные даты привязаны к исходному сообщению, включая уточнения после
полуночи. Найденное время поступает в исходном IANA-поясе, преобразование выполняет
domain. Для пользовательских повторов весенний пропуск времени сдвигается вперёд
на величину перехода, осенний повтор часа используется один раз, в первый момент.
Для найденного публичного события неоднозначное или несуществующее местное время
требует уточнения. Дата дела хранится без UTC-преобразования.

Просмотр будущих периодов вычисляет вхождения из серии и исключений без записи
в очередь; прошлое берётся из сохранённых вхождений. Изменения календаря и очереди
атомарны. Worker использует постоянную очередь и сохраняет прогресс отправки.
Условия доставки после простоя и её ограничения описаны в
[контракте внешнего поведения](../DEPLOYMENT.md#внешнее-поведение).

Оформление строится через `Text`, `Bold`, `Italic`, `Code` и Telegram entities
с явным `parse_mode=None`. Пользовательский и модельный текст отображается буквально.
Позиции entities и длина сообщений считаются в UTF-16. Длинные сводки делятся по
целым строкам с лимитом 3500 единиц UTF-16; части в БД остаются строками, оформление
добавляется при отправке. Начатая сводка сохраняет снимок и `part_index`.

Один процесс обслуживает polling и очередь. Остановка сначала завершает polling
и обработчики, затем закрывает соединения. Health отделён от runtime и SDK: его
чтение не должно запускать приложение. Точные требования к времени остановки,
порогам health и watchdog находятся в [DEPLOYMENT.md](../DEPLOYMENT.md).

## Автономные проверки

Основной набор работает без секретов, сети и настоящего Telegram:

```sh
python -m unittest discover -s tests -q
```

Он проверяет календарную арифметику и DST, SQLite и миграции на временных БД,
изоляцию пользователей, атомарность и отсутствие дублей, диалоги и кнопки,
поиск времени с подставным OpenAI API, источники и диагностический журнал,
доставку, восстановление, polling, watchdog и завершение задач aiogram.
Свежие процессы отдельно проверяют health с запретом импорта SDK, открытия
SQLite, записи файлов и сетевых обращений, включая приоритет окружения над
`--env-file`. Протокольный тест Unix datagram socket выполняется только на Linux.

Ruff нужен только разработчику:

```sh
python -m pip install ruff
ruff check calendar_bot tests
ruff format --check calendar_bot tests
```

Используйте управляемые часы и подставные API. После изменения зависимостей
проверяйте установку и тесты на Python 3.14; перед релизом набор должен пройти
на целевой платформе. Для правок только документации достаточно проверить
команды, пути, ссылки, соответствие исходникам и `git diff --check`.

## Платная evaluation

Живой разбор событий, дел и смешанного списка запускается отдельно и расходует
API-бюджет:

```sh
python -m calendar_bot.evaluation
```

Базовые сценарии проверяют также ежедневные повторы и несколько дней каждой
недели, полный список из десяти записей, уточнение для одиннадцати записей,
интервалов в несколько дней/недель, даты окончания серии и числа повторений.
Смешанный список с одним неподдерживаемым условием должен целиком потребовать
уточнения. Проверяются типы, поля и порядок записей либо отсутствие записей
с непустым вопросом; точная формулировка вопроса не фиксируется.

Отдельные сценарии редактирования проверяют смену названия, времени серии,
напоминаний и даты дела с сохранением всех остальных полей. Попытка сменить
тип дела или добавить новую запись при редактировании должна дать уточнение.

Автономные тесты с подставным API проверяют валидацию и управление попытками,
но не понимание текста моделью. Новые сценарии evaluation сами по себе не
подтверждают качество промпта: для этого нужен отдельный живой запуск.

Дополнительные поисковые сценарии включают финал Евро-2024, матч Англия — Испания
26.09.2026 с переводом BST в Ереван, продолжение диалога после ошибочного отказа,
неоднозначное и вымышленное событие:

```sh
python -m calendar_bot.evaluation --web-search
```

Ожидаемые моменты зафиксированы: финал — 14.07.2024 19:00 UTC
([UEFA](https://www.uefa.com/uefaeuro/history/news/0284-18bb952a9458-2a9e1ff202c4-1000--euro-2024-final-who-was-in-it-when-and-where-was-it/)),
матч Лиги наций — 26.09.2026 18:45 UTC
([England Football](https://www.englandfootball.com/articles/2026/Sep/11/when-are-england-men-playing-in-2026-27-season-20260911)).
Для финала используется летнее местное время Берлина; UEFA обозначает его как CET.
Живой поиск может менять результаты даже при неизменных датах и промпте.

Runner выводит выбранную модель и технические метрики. Для сохранения отчёта:

```sh
python -m calendar_bot.evaluation --web-search --report .cache/evaluation.json
```

У каждого сценария есть стабильный ID. Получить весь список без API и загрузки
секретов, а затем повторить только выбранный сценарий:

```sh
python -m calendar_bot.evaluation --list-cases
python -m calendar_bot.evaluation --web-search --case web_euro --repeat 3 --report .cache/euro.json
```

`--case` можно указать несколько раз; неизвестный ID завершает запуск до API.
Для выбора веб-сценария всё равно нужен `--web-search`. По умолчанию каждый
сценарий выполняется один раз; `--repeat` задаёт число платных разборов каждого
выбранного сценария. Повторы выполняются последовательно в одинаковом порядке,
с независимым контекстом каждого `parse`. Ошибка проверки или API не прерывает
остальные сценарии; прежнюю остановку на первой ошибке включает `--fail-fast`.

JSON содержит модель запроса и ответа, число и статус API-попыток, входные,
выходные, кешированные и reasoning-токены, число вызовов `web_search`, длительность
попыток и сводки по созданию/редактированию. В отчёте нет диалогов, ответов модели,
заголовков и тел SDK-ошибок. Пустые метрики обозначены `null`; суммы отражают только
ответы с доступными метаданными. Это технический отчёт, отдельный от приватного trace.

Формат `schema_version=2` дополняет метрики результатами сценариев: `case_id`,
номер повтора, длительность всего разбора с проверками, число записей, наличие
уточнения и статус. `passed` означает совпадение с ожиданиями, `failed` —
расхождение полей или формы результата с фиксированным кодом проверки, `error` —
исключение с безопасным именем типа. `cancelled` и `not_run` отмечают отменённый
и не начатый разбор. API-попытки привязаны к ID и номеру повтора; внутренняя
перепроверка источника остаётся частью того же сценария. `outcomes` содержит
счётчики статусов. Отдельные SHA-256 промптов и описаний выбранных сценариев позволяют
заметить изменение условий между отчётами.

Время измеряется монотонным `perf_counter` вокруг вызова SDK, включая получение
и разбор ответа. P50 — медиана, P95 — ближайший ранг вверх. Это задержка отдельной
API-попытки, а не всего пользовательского диалога. Повторная проверка даёт ещё
одну попытку. Поле `completed` истинно только если все запланированные проверки прошли;
`completed_responses` учитывает успешные ответы API, даже если проверка содержания
не прошла. `finished` означает, что все сценарии выполнены, включая неудачные.
Отмена и `--fail-fast` сохраняют частичный отчёт. Код выхода — 0 только при
`completed=true`, иначе 1. Текст ответов и поиска можно отдельно записать в
приватные JSONL, явно задав `OPENAI_TRACE_DIR`; правила хранения и ограничения
описаны в [диагностике модели](#диагностика-разбора).
Стоимость в валюте не рассчитывается; для сравнения прогонов учитывайте состав
сценариев, поиск, кеширование и возможные повторные попытки.

Нужны `OPENAI_API_KEY` и при необходимости `OPENAI_MODEL`. Evaluation не использует
Telegram и не входит в автономный набор. Живые проверки интерфейса выполняйте
с отдельным тестовым ботом; сценарии готовности к эксплуатации перечислены в
[проверке релиза](../DEPLOYMENT.md#проверка-релиза).

## Обновление зависимостей

Исходные ограничения находятся в [requirements.in](../requirements.in),
production устанавливает [requirements.txt](../requirements.txt) с хешами.
Пересоздание lock через uv:

```sh
uv pip compile requirements.in --universal --python-version 3.14 --generate-hashes --output-file requirements.txt
```

После обновления установите зависимости с `--require-hashes` и повторите проверки.
Не редактируйте lock вручную. uv не требуется для запуска приложения.

## Диагностика разбора

В [.env.example](../.env.example) уже задано
`OPENAI_TRACE_DIR=data/model-traces`. После настройки из примера диагностика
включена. Для существующей установки задайте переменную в окружении процесса
и перезапустите бот. Пустое значение `OPENAI_TRACE_DIR=` отключает запись после
перезапуска. Переменные окружения имеют приоритет над файлом конфигурации.

Каждый разбор создаёт отдельный `model-trace-<случайный ID>.jsonl`, включая
повторную проверку времени. Записи содержат входной диалог и инструкции,
ответ модели, поисковые запросы и источники, структурированные поля,
вычисленные моменты в UTC и поясе пользователя, число токенов и тип ошибки.
Для ошибки времени сопоставьте исходную дату и пояс, поля ответа и рассчитанные
`start_utc` / `start_user`. `future_at_reference` относится к моменту исходного
сообщения; окончательную проверку перед записью выполняет service по текущим часам.
Наличие успешного ответа модели в файле само по себе не подтверждает запись в БД.

Файлы содержат личный текст. Не публикуйте их вместе с журналом экспериментов;
для отчётов используйте обезличенные или синтетические примеры. Ключи конфигурации,
HTTP-заголовки, тела SDK-ошибок и внутренние рассуждения не записываются.
Предупреждения сериализации Pydantic, способные включать фрагменты ответа SDK,
подавляются в `logging_config.py`; прочие предупреждения остаются доступными.
Ошибка записи диагностики не останавливает разбор, в обычный журнал попадает
только безопасный тип ошибки. Требования к каталогу, лимиты и очистка описаны в
[состоянии и записи](../DEPLOYMENT.md#состояние-и-запись).

## Диагностика polling

Для работающего процесса с тем же `DATABASE_PATH`:

```sh
python -B -m calendar_bot health
```

Команда проверяет технический снимок и владельца OS-lock без сети и открытия
SQLite. Код `0` означает успешную проверку polling, код `1` сопровождается
безопасной причиной, возрастом последнего успеха и типом ошибки. Точные пороги,
протокол watchdog и требования к реакции окружения описаны в
[контроле polling](../DEPLOYMENT.md#контроль-polling).

В обычном журнале ищите `polling_request_failed` с типом исключения,
`polling_recovered` после восстановления и `polling_stalled` при отсутствии
прогресса. Продолжающиеся попытки при недоступности Telegram отличаются от
зависания: неуспешный health сам по себе не служит основанием для рестарта.
Успешный health не проверяет OpenAI и доставку напоминаний.

## Замер запуска health

Для сравнения двух версий используйте
[tools/benchmark_health.py](../tools/benchmark_health.py). Нужны Linux, Python 3.14
с зависимостями проекта и GNU time (`/usr/bin/time`, инструмент измерения).
Подготовьте две отдельные копии `calendar_bot/` и одинакового `requirements.txt`
без `__pycache__`, например через `git archive`. Задайте переменные
`BASELINE_SOURCE` и `CURRENT_SOURCE` путями к этим копиям, затем из корня
репозитория запустите:

```sh
python tools/benchmark_health.py --before "$BASELINE_SOURCE" --after "$CURRENT_SOURCE" --runs 15 --warmups 2 > health-startup.json
```

Инструмент запускает новые процессы `python -B -m calendar_bot health --env-file /dev/null`,
чередует порядок версий, удерживает временный lock и обновляет синтетический
технический снимок. SQLite не создаётся, файлы `.env` сравниваемых копий и внешние
API не используются. GNU time измеряет CPU с точностью 0,01 секунды и пик RSS
самого health-процесса; `perf_counter` — длительность вместе с обёрткой измерения.
JSON содержит наблюдения, версии пакетов и сводку.

Измерения запускаются отдельно от unit-тестов, без нестабильных временных порогов
успеха. Условия, выбранные версии, результаты и ограничения конкретного замера
фиксируйте в [журнале](journal/README.md). Первый сохранённый
[отчёт](journal/2026-09-25-health-startup.md) относится к замеру 25 сентября 2026 года.

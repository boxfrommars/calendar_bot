# Оптимизация запуска health

[Журнал работ](README.md) · [Методика повторного замера](../development.md#замер-запуска-health)

Дата исходного замера: **25 сентября 2026 года**. Отчёт перенесён из README
при разделении документации. При переносе замер не повторялся; значения ниже
сохранены из первоначального отчёта.

## Задача

Периодическая команда `health` должна читать техническое состояние процесса
и проверять владельца OS-lock. Загрузка SDK и runtime бота при каждом запуске
создавала лишние затраты CPU, времени и памяти. Цель — сократить стоимость
проверки, сохранив её поведение.

  кеш зависимостей был общим.

## Изменения

Чтение и проверка снимка вынесены из модуля наблюдения за polling в отдельный
лёгкий модуль. CLI загружает зависимости работающего бота после выбора команды.
Для `health` не требуются aiogram, OpenAI SDK, Pydantic, HTTP- и SQLite-клиенты.

Формат снимка и результата, проверка владельца lock, пороги и watchdog-протокол
сохранены. Дополнительная миграция данных для этой оптимизации не требовалась.
Связанные файлы: [health.py](../../calendar_bot/health.py),
[CLI](../../calendar_bot/__main__.py),
[проверки изоляции CLI](../../tests/test_health_cli.py).

## Методика и результаты

Использовался [инструмент измерения](../../tools/benchmark_health.py).
После **двух прогревов** каждой версии выполнено **по 15 новых процессов**
с чередованием порядка версий. Измеряемая команда:
`python -B -m calendar_bot health --env-file /dev/null`.
Каждый процесс вернул успешный health на синтетическом снимке и настоящем
OS-lock. Файл SQLite не создавался, секреты и внешние API не использовались.

GNU time измерял CPU (user + system) с точностью 0,01 секунды и пик RSS самого
health-процесса. `perf_counter` измерял длительность запуска вместе с обёрткой
измерения.

| Среднее за запуск | До | После |
| --- | ---: | ---: |
| CPU, user + system | 5,250 с | 0,073 с |
| Длительность | 5,264 с | 0,089 с |
| Пик RSS процесса | 197,5 МиБ | 20,1 МиБ |

CPU-время уменьшилось примерно на **98,6%**, пик RSS — на **89,8%**.

## Выводы и ограничения

Изоляция health существенно снизила стоимость отдельной проверки на данном
локальном Linux-стенде. Результаты не характеризуют постоянную память основного
бота или учёт памяти службы systemd. Числа зависят от окружения и состояния кешей;
они не являются порогами успеха для unit-тестов или гарантией для другой машины.

В исходном README сохранены средние значения и условия; полный JSON наблюдений
в эту запись не добавлялся. Для новых сравнений следует сохранить собственный
результат инструмента и оформить новую запись с фактическими версиями и условиями.
Актуальные требования к health находятся в
[контракте размещения](../../DEPLOYMENT.md#контроль-polling).

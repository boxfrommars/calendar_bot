# Обновление certifi после компрометации цепочки emSign

## Задача

Устранить доверие к цепочке скомпрометированных промежуточных CA eMudhra/emSign
обновлением certifi и сохранить нижнюю границу безопасности при генерации lock.

До изменения репозиторий и локальное окружение содержали certifi 2026.7.22.
[Advisory проекта GHSA-6q48-6c7w-9gw2](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2)
указывает исправление в 2026.10.18.
[Обновлённая запись GHSA](https://github.com/advisories/GHSA-6q48-6c7w-9gw2)
рекомендует 2026.10.19 или новее: версия 2026.10.19 вернула незатронутые корни
emSign после удаления всех корней этого CA в 2026.10.18.

## Контекст и условия

- Дата работы: 2026-10-27; исходная версия репозитория: `8e1d8f6`.
- Локальная проверка: Windows, Python 3.14.8, Ruff 0.16.8, существующее
  виртуальное окружение проекта.
- Служебные инструменты обновлены с pip 26.2.1 и uv 0.12.18 до pip 26.2.2 и
  uv 0.13.4. Официальные wheels загружены с PyPI; SHA-256 метаданных и файлов
  сверены с опубликованными хешами
  [pip](https://pypi.org/project/pip/26.2.2/) и
  [uv](https://pypi.org/project/uv/0.13.4/).
- Минимумы инструментов и безопасное первичное обновление описаны в
  [официальном сообщении Python](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576).
  Обновление certifi приложения не заменяет собственные CA bundles pip и uv.

## Изменения

В исходные ограничения добавлено `certifi>=2026.10.19` со ссылкой на GHSA.
Lock пересоздан обычной командой, без указания точной версии certifi:

```sh
uv pip compile requirements.in --universal --python-version 3.14 --generate-hashes --output-file requirements.txt --cache-dir .cache/uv
```

uv выбрал certifi 2026.10.23. Версия и оба SHA-256 в lock соответствуют
[релизу на PyPI](https://pypi.org/project/certifi/2026.10.23/).
Сравнение содержимого lock без блока certifi подтвердило, что остальные версии,
хеши и комментарии зависимостей не изменились.

В руководстве разработки и контракте размещения отражены минимумы безопасности
и проверка CA bundle. Код приложения и схема БД не менялись.

## Проверка и результаты

На Python 3.14.8 успешно выполнены установка через
`python -m pip install --require-hashes -r requirements.txt` и `python -m pip check`.
Установленная версия certifi — 2026.10.23.

Проверка стандартной библиотекой вычислила SHA-256 DER каждого из 118 сертификатов
в PEM bundle. Корень `emSign ECC Root CA - G3` с отпечатком
`86a1ecba089c4a8d3bbe2734c612ba341d813e043cf9e8a862cd5c57a36bbe6b`
отсутствует. Затем bundle явно загружен в `ssl.SSLContext`; среди 118 загруженных
CA этот отпечаток также отсутствует. Сетевые TLS-запросы для проверки не нужны.

Команды автономной проверки из окружения Python 3.14:

```sh
python -m unittest discover -s tests -q
ruff check calendar_bot tests
ruff format --check calendar_bot tests
```

Полный набор: 218 тестов, успешно; один интеграционный тест Unix datagram socket
пропущен на Windows по условию платформы. Набор выполнен вне sandbox из-за
ограничений на локальные сокеты Windows asyncio; использовались синтетические
данные и подставные внешние API.

Ruff lint и проверка формата прошли: 37 Python-файлов соответствуют формату.
Локальные ссылки затронутой документации и `git diff --check` проверены.

## Ограничения

Проверка относится к certifi в окружении этого проекта. Production-развёртывание,
системное хранилище сертификатов и другие окружения не изменялись. Рабочий бот,
пользовательская БД и платная OpenAI evaluation не использовались. Прогон на Linux
не выполнялся.

# Описание поля question и выбор результата

[Журнал работ](README.md) · [Сравнение reasoning](2026-09-27-reasoning-effort.md)

Дата работы: **27 сентября 2026 года**.

## Задача и основание

Дополнительное чтение трёх отказов `low` из предыдущего сравнения показало:
во всех поисковых запросах была правильная абсолютная дата. Для финала Евро
модель назвала правильное время, но ошибочно сочла событие прошедшим относительно
контекста. В продолжении диалога об Англии — Испании она правильно исправила
время и оценку прошлого, но вернула объяснение без записи. В запросе о Чехии —
Англии после поиска спросила время напоминания; по трассировке нельзя установить,
нашла ли время начала: содержимое поисковой выдачи и страниц не сохраняется.
Эта диагностика выполнена без новых API-вызовов и не устанавливает внутренние
причины решений модели.

Гипотеза с готовыми календарными датами отложена: наблюдаемые запросы уже содержат
правильные даты. Большой блок правил выбора `items`/`question` ранее
[не дал улучшения](2026-09-27-output-choice.md). Здесь проверяется другой способ
передачи условия: описание поля `question` в JSON-схеме, без правки промпта.
[OpenAI Docs](https://developers.openai.com/api/docs/guides/structured-outputs)
рекомендует ясные описания важных полей и проверку через evaluation; улучшение
для данной модели и задачи требует измерения.

## Кандидат и условия

Контроль — `b39272a`. У `question` сохраняется тип `str | None` и обязательность;
в API добавляется только `description`:

```text
Короткий вопрос пользователю только при нехватке данных, неоднозначности
или неподдерживаемом условии хотя бы одной записи. Иначе null, а полный
список записей — в items. Не используй question для справочного ответа
о найденном времени, извинения или сообщения, что событие прошло:
при подтверждённых полях верни записи, проверку прошлого выполняет приложение.
```

Точный текст передаётся одной строкой с пробелами на месте переносов выше.
Остальные поля, их порядок, типы, обязательность и ограничения, имя схемы
`ParseResult`, strict-режим, инструкции, роли и диалоги одинаковы. Сравнение
форматов после преобразования установленным SDK подтвердило единственное
различие — `schema.properties.question.description`.

Временный сценарий использует `EvaluationRun` и `EvaluationClient`.
Для кандидата `pydantic.create_model` создаёт совместимый `ParseResult` с одним
описанием поля; на время последовательного разбора подставляется только класс
схемы. Рабочий parser во время сравнения не редактируется. Новых зависимостей,
модельных этапов и переменных окружения приложения нет.

Среда: Windows, Python 3.14.7, OpenAI SDK 2.54.0, Pydantic 2.13.5, Ruff 0.16.8.
Модель — `gpt-6-luna`, `reasoning.effort=low`, `store=False`,
`max_output_tokens=3000`, SDK timeout 30 секунд, SDK-повторы отключены.
На весь `parse` остаются 40 секунд, три веб-вызова и одна перепроверка.

## Методика и условия принятия

До первого API-вызова зафиксированы **80 платных разборов**, 40 на вариант:
восемь сценариев, пять повторов. Порядок вариантов чередуется между парами
одного сценария и повторами.

- Положительные: `web_euro`, `web_euro_followup`, `web_bst`, `web_bst_followup`,
  `web_czechia_2026`, `web_czechia_2026_followup`.
- Защитные: `personal_missing_time` и `event_duration`, требующие уточнения
  без поиска личных событий.

Опорные даты и ожидаемые моменты берутся из постоянной evaluation. На дату
запуска финал Евро и Англия — Испания исторические, Чехия — Англия предстоящий;
относительно контекста приложения все три матча будущие. Поиск живой.

Условия перехода к полному платному набору из 33 сценариев:

- Больше успешных положительных разборов и меньше пустых списков с вопросом
  до валидации приложения.
- Все десять защитных разборов кандидата проходят без веб-вызовов.
- Разборов с неподтверждёнными URL не больше контроля.
- Оба варианта завершают все API-попытки; диагностика полная, исходные бюджеты
  соблюдены.
- P95 всего `parse` кандидата не больше 30 секунд и не больше удвоенного P95
  контроля. Это условие эксперимента, не изменение runtime-таймаута.
- Для принятия дополнительно требуется прохождение всех 33 сценариев полного
  набора одним прогоном. Повторы ради другого результата не предусмотрены.

Хеши входов, промптов и набора должны совпасть. Параметры API должны совпасть
после нормализации только описания `question`. Отдельно сохраняются хеши
фактических SDK-форматов и описания; основной trace схему ответа не содержит.
Счётчики вопросов и неподтверждённых URL собираются до валидации parser.
Приватные ответы, поисковые тексты и URL в репозиторий не переносятся.

## Полный набор и решение

[Полный прогон](2026-09-27-question-description-full.json) выполнен один раз:
**32/33 прошли, один технический `AttributeError`, ноль расхождений полей**.
Все 25 сценариев без поиска и семь из восьми поисковых прошли. Не завершился
на уровне parser сценарий `web_bst`; сам API-ответ имел статус `completed`.
Все 33 API-попытки завершились, trace содержит 33 запроса и 33 ответа без усечения.
Метрики: 9 веб-вызовов, 252261 входной токен, 5008 выходных, 211032 кешированных,
2396 reasoning-токенов; суммарное время API 87,3486 с.

Кандидат **отложен, в рабочую схему не включён**: условие прохождения всех
33 сценариев не выполнено. Это не свидетельство ухудшения ответов из-за описания:
трассировка сбойного случая содержит правильное событие с URL из метаданных
первого поиска, началом 26.09.2026 18:45 UTC и корректным признаком будущего
относительно контекста.
Однако исходный результат полного прогона остаётся технической ошибкой.
После исправления приложения живой полный набор не повторялся; без такой проверки
нельзя объявлять кандидат принятым или полный прогон успешным.

## Найденный дефект обработки метаданных

В ответе сбойного сценария два завершённых `web_search_call`. Первый содержал
URL, совпадающий с источником события. В сохранённой диагностике второго все
поля действия были `null`, список источников пуст. Диагностика сохраняет
выбранные атрибуты, а не исходное представление объекта SDK, поэтому не позволяет
отличить `action=null` от другого объекта без доступных атрибутов.

`search_urls` обращался напрямую к `action.type`, `action.sources` и атрибутам
источников. Автономный ответ через настоящий SDK и `httpx.MockTransport`,
сочетающий корректный поиск и завершённый вызов с `action=null`, воспроизвёл
`AttributeError` на обращении к `action.type`. Это подтверждённый дефект кода,
совместимый с наблюдавшейся трассировкой; точный исходный объект провайдера
не восстанавливался и новый платный запрос для диагностики не выполнялся.

Обработка теперь проверяет доступность метаданных перед чтением полей.
Неизвестное или неполное действие не даёт разрешённых URL и не отменяет ссылки,
уже подтверждённые другим корректным вызовом того же ответа. Для результатов
поиска принимаются только строковые URL с типом источника `url`; для открытия
и поиска на странице нужен распознанный тип действия и строковый URL.
Точное сравнение ссылок, проверка HTTP(S), атомарность списка и бюджеты сохранены.
Если источник события не подтверждён ни одним вызовом, возвращается уточнение.

В существующую SDK-регрессию добавлен завершённый вызов с пустым действием:
до исправления тест падал, после проходит. Дополнительная автономная регрессия
проверяет восемь форм неполных/неизвестных метаданных в двух условиях: с отдельным
подтверждённым источником и без него. Во втором случае смешанный список событий
и дел целиком остаётся несохранённым. Проверки выполняются без сети и секретов.

## Ограничения и проверки

Пять повторов не устанавливают устойчивую частоту ошибок; предварительное
преимущество составляет один разбор. Поиск и кеширование не фиксировались,
нагрузка машины не контролировалась; две пары сценариев исторические в реальном
мире. Описание поля не гарантирует правильного выбора формы ответа.
Проведено ровно **113 платных разборов**: 80 для сравнения и 33 для полного набора.
Новый дефект проверен и исправлен автономно; результаты оплаченного набора
после этого не переписывались. Ретроспективная диагностика использовала только
синтетические данные. Приватные JSONL в репозиторий не включены.

До сравнения прошли 46 профильных тестов, после исправления метаданных — 47.
Полный `unittest` на Python 3.14.7: **210 тестов**, `OK (skipped=1)`;
Unix datagram socket ожидаемо пропущен на Windows. Ruff, форматирование,
`git diff --check` и 149 локальных ссылок и якорей документации прошли.
Проверка AST подтвердила, что изменение parser ограничено `search_urls`;
хеш рабочего SDK-формата совпадает с контролем. На Linux проверки не выполнялись.

Рабочая модель остаётся `gpt-6-luna`, reasoning — `low`; промпты и описание
`question` в рабочей схеме не менялись. Production, Telegram, пользовательская
БД, `.env`, зависимости и интерфейс `Parser.parse` не затрагивались.
